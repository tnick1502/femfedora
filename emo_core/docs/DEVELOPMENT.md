# Разработка и проверки

Рабочая директория — самостоятельный проект `emo_core/`. Правила изменений находятся в [AGENTS.md](../AGENTS.md), требования — в [ORIGINAL_SPEC.md](ORIGINAL_SPEC.md). Код родительского проекта не импортируется.

## Окружение Poetry

```bash
poetry env use python3.12
poetry install
poetry run emo-config init-env
poetry run emo-config check-config
```

Используется Poetry 2.x. Метаданные пакета и CLI находятся в стандартном `[project]`, зависимости и группы — в настройках Poetry. Поддерживаемый диапазон — Python `>=3.12,<3.15`. `poetry.toml` включает `.venv` внутри проекта; зависимости фиксирует `poetry.lock`. Новые зависимости добавляются через Poetry, а не в окружение родительского проекта.

Для запуска API вне Docker укажите доступный хост PostgreSQL в `DATABASE_URL`: имя `db` из Compose не разрешается автоматически на хосте. Затем:

```bash
poetry run alembic upgrade head
poetry run uvicorn emo_core.main:app --port 8086 --no-access-log
```

Worker запускается отдельным процессом из той же папки:

```bash
poetry run python -m emo_core.workers.proactive_worker
```

Режим разработки Compose:

```bash
bash tools/dev_up.sh
```

Скрипт собирает и запускает Compose с `docker-compose.dev.yml`. Код, политики, `tools/` и `demo/` подключаются с хоста; Uvicorn следит за Python-кодом. Повторный запуск применяет новые миграции. Сводка запуска сохраняется в `../tmp/live/`. Такой запуск может перезапустить текущий стенд — учитывайте совместную работу над ним.

## Быстрые проверки

```bash
poetry run pytest -q
poetry run ruff check .
poetry run ruff format --check .
poetry check
```

По умолчанию фикстуры создают временные SQLite-базы, используют явный mock и не вызывают внешние модели. Проверки PostgreSQL пропускаются. Текущий результат приведён в [VERIFICATION.md](VERIFICATION.md); число тестов не является постоянным свойством проекта.

Для выбранной правки запускайте подходящие существующие тесты. Изоляция, блокировки и миграции требуют PostgreSQL: SQLite не подтверждает работу `FOR UPDATE`/`SKIP LOCKED` и составных ограничений в PostgreSQL.

## Изолированный PostgreSQL

**Фикстура `sessions` выполняет `drop_all` и `create_all` перед каждым тестом. `TEST_DATABASE_URL` должен вести только в отдельную расходуемую БД.** Не используйте DSN демо или основной установки.

Пример отдельного контейнера с тестовым паролем:

```bash
docker run --rm -d --name emo-core-tests \
  -p 127.0.0.1:55439:5432 \
  -e POSTGRES_USER=emo -e POSTGRES_PASSWORD=emo_test_only \
  -e POSTGRES_DB=emo_test postgres:16-alpine

docker exec emo-core-tests pg_isready -U emo -d emo_test
TEST_DATABASE_URL=postgresql+asyncpg://emo:emo_test_only@127.0.0.1:55439/emo_test \
  poetry run pytest -q
```

Дождитесь успешного `pg_isready` перед pytest. Если порт занят, выберите другой. Команда остановки ниже удаляет именно этот временный контейнер и его расходуемые данные:

```bash
docker stop emo-core-tests
```

## Миграции

Тесты ORM пересоздают схему и не заменяют проверку Alembic. Для миграций используйте вторую отдельную базу в тестовом контейнере:

```bash
docker exec emo-core-tests createdb -U emo emo_migrations
export DATABASE_URL=postgresql+asyncpg://emo:emo_test_only@127.0.0.1:55439/emo_migrations
export APP_ENV=test AI_MODE=disabled
poetry run alembic upgrade head
poetry run alembic check
poetry run alembic downgrade base
poetry run alembic upgrade head
poetry run alembic check
```

`downgrade base` удаляет таблицы и данные; выполняйте этот цикл только на расходуемой базе. После проверки закройте эту оболочку или снимите временные переменные, прежде чем работать с обычным стендом.

Применённые миграции сохраняются как история схемы. Замороженный `alembic/data/questionnaires_20261110_v1.json` не редактируется при выпуске новой редакции. Изменение создаётся новой ревизией; при затрагивании данных отдельно проверяется переход со старой схемы с уже существующими записями.

## Проверки живых моделей

```bash
bash tools/run_live_check.sh
```

Скрипт собирает и запускает текущий Compose, затем обращается к реально настроенным моделям. Это внешние API-вызовы, которые могут тарифицироваться. Перед чатом он переключает общий режим в live и сбрасывает обе выбранные роли к профилям из `.env`; это влияет на следующие сообщения всех пользователей. Использует синтетические сценарии, создаёт беседы профиля `maria` и включает этому профилю согласие на внешнюю обработку. Результаты с синтетическими текстами и ответами сохраняются в `../tmp/live/`.

Для уже работающего стенда можно отдельно вызвать:

```bash
docker compose exec -T api python tools/live_check.py calibrate
docker compose exec -T api python tools/live_check.py chat
```

`calibrate` проверяет маркеры Jev, `chat` — API чата и отчёты полного конвейера. Такие прогоны не являются клинической проверкой. Не переносите в набор личную переписку. Параметры провайдеров и предварительные пороги описаны в [CONFIGURATION.md](CONFIGURATION.md).

## Описания Python-функций

Docstring пишется по-русски и описывает фактическое поведение. Для простого помощника достаточно одной строки. Для вычислений и сервисных операций указывайте смысл результата, значимые параметры, единицы измерения, условия отказа и побочные эффекты. Для async-кода отмечайте границы транзакции и внешние вызовы, если они влияют на использование.

Не пересказывайте имя функции и каждую строку реализации. Не обещайте клиническую корректность по наличию технической проверки. `flush` не называйте `commit`, условный кэш — постоянным хранилищем, приблизительную оценку — точным подсчётом.

Пример из механизма шкал:

```python
def score_answers(questionnaire, answers, complete):
    """Возвращает сумму по ключам пунктов и список сработавших safety-пунктов.

    В черновике сумма равна None, но safety-пункты проверяются сразу. Для complete
    нужны все основные ответы, иначе HTTP 422. Дополнительные вопросы сюда не входят.
    """
```

При правке только описаний не меняйте сигнатуры, условия, запросы и значения. Для этой редакции до/после сравнивалось AST всех Python-файлов с исключением docstring; исполняемая структура совпала. Это дополняет тесты, а не заменяет их.

## Документация и история

[IMPLEMENTATION.md](IMPLEMENTATION.md) описывает текущее соответствие ТЗ, [VERIFICATION.md](VERIFICATION.md) — последний проверенный срез. Старые записи сохранены отдельно в [history/README.md](history/README.md): их результаты относятся к прошлым версиям, а не к текущему дереву файлов.

Перед изменениями читайте относящиеся разделы исходного задания. После обновляйте текущие документы, сохраняя честное различие между выполненной проверкой, прежними результатами и тем, что ещё не проверялось. Клинические источники, формулировки и статусы одобрения не исправляются как обычная редактура.
