**Версия:** 1.0

**AI:** подключаемая LLM + TypeSafe Jev

# 0. Твоя задача как разработчика

Необходимо самостоятельно реализовать полностью функционирующую систему EMO Core по приведённому техническому заданию.

Не ограничивайся проектированием архитектуры, написанием отдельных примеров или созданием пустых интерфейсов. Создай законченный backend-проект с базой данных, миграциями, REST API, AI-интеграциями, сохранением персонального контекста, психологическими опросниками, анализом жалоб, мониторингом самочувствия и инициативной отправкой сообщений.

Проект должен запускаться через Docker Compose, иметь автоматические тесты, документацию и минимальный демонстрационный веб-интерфейс для ручной проверки.

Реализацию проводи поэтапно. После каждого этапа проверяй работоспособность. Исправляй найденные ошибки самостоятельно.

Если для полноценной работы требуются реальные API-ключи, предоставь конфигурацию через переменные окружения и работающие mock-провайдеры для локальных тестов. Не записывай секреты в исходный код.

Если для использования опросника необходима лицензированная русскоязычная редакция или утверждённые клинические пороги, реализуй все механизмы, но не выдумывай содержание или юридическое разрешение на использование материала. Такой опросник должен оставаться недоступным для публичного применения до корректной конфигурации.

**Главное требование:** работоспособное многопользовательское ядро, а не демонстрация отдельных возможностей.

# 1. Назначение системы

EMO Core — самостоятельный backend-модуль для приложения сопровождения беременности.

Его основная функция — естественное эмоционально поддерживающее общение с женщиной во время беременности и после родов.

Система должна:

1. Общаться с женщиной через выбранную LLM.
2. Запоминать важные обстоятельства, переживания и предпочтения.
3. Анализировать сообщения и извлекать эмоциональные жалобы.
4. Вести историю жалоб и их изменений.
5. Предлагать валидированные психологические опросники.
6. Сохранять каждое прохождение опросника.
7. Вычислять баллы и отслеживать динамику результатов.
8. Собирать добровольные самооценки настроения и тревоги.
9. Выбирать подходящий протокол психологической поддержки.
10. Проверять безопасность генерируемых ответов.
11. Рекомендовать профессиональную помощь при соответствующих основаниях.
12. Самостоятельно инициировать сообщения в чат по расписанию и событиям.
13. Работать с множеством пользователей с изолированными историями.

Система **не ставит психиатрические или психологические диагнозы, не назначает лечение, не заменяет врача или психолога и не должна позиционироваться как медицинское средство диагностики**.

Результаты опросников являются показателями самооценки симптомов и основаниями для дальнейшего обсуждения или обращения к специалисту.

# 2. Общая архитектура

Реализовать один FastAPI backend, PostgreSQL и один отдельный процесс фонового планировщика.

Логическая схема:

```text
                    PREGNANCY APPLICATION
                             |
                      REST API / JWT
                             |
                       EMO CORE API
                             |
                +------------+------------+
                |                         |
           CHAT PIPELINE             DATA / API
                |                         |
         Input Safety Guard        Questionnaires
                |                   Check-ins
         Jev Emotion Analyzer       Complaints
                |                   Trends
         State Evaluator                 |
                |                         |
         Context Builder                 |
                |                         |
         Protocol Selector               |
                |                         |
         Adaptive Support LLM            |
                |                         |
         Output Safety Guard             |
                |                         |
         Response Persistence            |
                |                         |
                +------------+------------+
                             |
                         PostgreSQL
                             |
                    PROACTIVE WORKER
                             |
                 Scheduler / Due Events
                             |
```

Система должна быть модульным монолитом.

- Kubernetes;

- Redis;

- мультиагентный фреймворк;
- отдельные нейронные сети прогнозирования депрессии;
- сложную систему RAG.

Всё перечисленное не требуется для MVP.

# 4. Многопользовательская модель

EMO Core является частью большего приложения.

Основной идентификатор пользователя поступает из авторизационного токена.

Поле `user_id` запрещено принимать как произвольный доверенный идентификатор в пользовательских запросах.

Каждый пользователь имеет собственные:

- диалоги;
- сообщения;
- эмоциональную память;
- жалобы;
- самооценки самочувствия;
- результаты опросников;
- персональное расписание;
- инициативные сообщения;
- настройки коммуникации.

По возможности поддержать `pregnancy_id` для привязки данных к конкретной беременности.

Срок беременности, предполагаемую дату родов и дату фактических родов желательно получать из основного приложения. Не создавать вторую независимую систему акушерского календаря.

Реализовать изоляцию данных на уровне всех запросов SQLAlchemy, проверку владения объектами и, по возможности, PostgreSQL Row-Level Security.

Все даты хранить в UTC, а локальное время вычислять по IANA timezone пользователя.

# 6. Chat Engine — основной цикл общения

При новом сообщении выполнить следующую последовательность.

## Шаг 1. Авторизация

Проверить пользователя и владение беседой.

## Шаг 2. Сохранение сообщения

Записать пользовательский текст и время.

Проверить `client_message_id`, чтобы повторный запрос не создавал новые сообщения и повторные AI-вызовы.

## Шаг 3. Input Safety Guard

Проверить сообщение на потенциально опасные признаки.

Сначала применить простые детерминированные правила, затем структурированную оценку Jev.

Если выявлена возможная непосредственная опасность, обычный диалог заменяется утверждённым сценарием безопасности.

Не использовать одни только ключевые слова как достаточное доказательство безопасности или её отсутствия.

## Шаг 4. Emotion Analyzer

Обработать сообщение через Jev.

Получить:

- основное намерение;
- эмоциональные маркеры;
- возможные жалобы;
- признаки ухудшения;
- признаки субъективного улучшения;
- необходимость уточнения;
- сигналы безопасности.

## Шаг 5. Complaint Manager

Обновить активные жалобы и сохранить отдельные события наблюдений.

## Шаг 6. Context Builder

Загрузить:

- последние 12–20 сообщений;
- краткую долговременную память;
- актуальные жалобы;
- последние результаты EPDS/GAD;
- последние check-in;
- предпочтения общения;
- состояние беременности или послеродового периода.

Не отправлять автоматически всю историю переписки в LLM.

## Шаг 7. State Evaluator

Определить текущую потребность в поддержке, необходимость обращения к специалисту и допустимые следующие действия.

## Шаг 8. Support Protocol Selector

Выбрать протокол общения.

## Шаг 9. LLM Generation

Сформировать ответ с помощью подключённой LLM.

## Шаг 10. Output Safety Guard

Проверить ответ на нарушения.

При необходимости выполнить одну попытку исправления. Если проверка повторно не пройдена — использовать безопасный заранее утверждённый текст.

## Шаг 11. Persistence

Сохранить ответ, выбранный протокол, версию правил и дополнительные события.

## Шаг 12. Memory Update

При необходимости обновить долговременную память.

Обновление резюме допускается выполнять через background worker, чтобы не задерживать ответ пользователю.

Для критически важных фактов и результатов опросников нельзя полагаться исключительно на отложенное обновление памяти.

# 7. Jev Emotion Analyzer

Использовать TypeSafe Jev как классификатор, а не как генератор ответов.

Официальная документация: https://docs.typesafe.ai/

API: https://api.typesafe.ai/v1/systemone

Поддерживаемые основные типы вопросов:

- `choice`;
- `noul`;
- `score`.

Для нескольких независимых признаков использовать отдельные `noul`-вопросы в одном запросе. Не выбирать одну эмоцию из списка, поскольку одновременно могут присутствовать несколько переживаний.

## 7.1. Словарь эмоциональных жалоб

Реализовать фиксированные категории:

```text
anxiety
fear_for_baby
low_mood
loss_of_interest
sleep_problem
fatigue
irritability
loneliness
relationship_stress
overwhelm
physical_discomfort
```

Дополнительно анализировать:

```text
self_reported_improvement
self_reported_worsening
functional_impact
request_for_support
request_for_medical_advice
need_for_clarification
possible_self_harm
possible_urgent_medical_issue
possible_psychosis
```

Эти категории являются наблюдаемыми маркерами текста, а не диагнозами.

## 7.2. Принципы анализа

Для каждого маркера Jev отвечает на атомарный вопрос.

Например:

- Сообщает ли женщина о собственных текущих трудностях со сном?
- Выражает ли она опасения относительно здоровья ребёнка?
- Сообщает ли она об ухудшении своего самочувствия?
- Упоминает ли она непосредственное намерение причинить себе вред?
- Содержит ли текст отрицание симптома, а не сообщение о его наличии?

Отдельно обрабатывать отрицание, цитирование чужих слов и события прошлого.

Нельзя интерпретировать вероятность `noul=0.9` как 90-процентную вероятность заболевания.

Пороги классификации должны храниться в конфигурации и проверяться на размеченных русскоязычных данных. Нельзя считать их клинически валидированными без проверки.

Jev не возвращает автоматически полный структурированный список медицинских жалоб. Классификацию и группировку выполняет код; связь с исходным текстом обеспечивается `message_id`.

Если Jev недоступен, не подменять результат выдуманными оценками. Применять консервативную ограниченную обработку, регистрировать техническую ошибку и при необходимости использовать безопасный шаблон ответа.

# 8. Complaint Manager

Система должна аккумулировать жалобы во времени.

Для каждой категории хранить:

- дату первого упоминания;
- дату последнего упоминания;
- количество подтверждённых упоминаний;
- связанные сообщения;
- прямые пользовательские оценки выраженности;
- сообщения об улучшении и ухудшении;
- актуальный статус.

Статусы:

```text
new
active
improving
resolved
unknown
```

Статус `resolved` присваивать только по достаточным прямым данным, например когда женщина сама говорит, что проблема исчезла.

**Не путать частоту сообщений с выраженностью проблемы.** Десять сообщений о тревоге не означают автоматически, что тревога в десять раз сильнее.

Отсутствие сообщений не должно трактоваться как улучшение.

# 9. Screening Engine

Поддержать четыре инструмента:

| Опросник | Использование |
|---|---|
| EPDS | Основная оценка перинатальных депрессивных симптомов |
| GAD-2 | Краткий скрининг тревожных симптомов |
| GAD-7 | Более подробная оценка тревоги |
| PHQ-9 | Опциональная альтернатива EPDS |

Для первой версии активировать EPDS, GAD-2 и GAD-7 после проверки корректности текстов, правил подсчёта, русскоязычной редакции и условий использования. PHQ-9 поддержать архитектурно, но не предлагать одновременно с EPDS без установленного основания.

Каждый опросник хранить как версионированную конфигурацию.

Подсчёт баллов должен быть реализован на Python.

LLM и Jev не имеют права вычислять или изменять итоговые баллы.

## 9.1. Основные правила

GAD-2:

- два вопроса;
- результат 0–6;
- при результате от 3 баллов предложить GAD-7 или профессиональную оценку.

GAD-7:

- семь вопросов;
- результат 0–21;
- хранить исходные ответы и баллы.

EPDS:

- десять вопросов;
- результат 0–30;
- учитывать реверсивные вопросы в соответствии с официальным ключом;
- пороги интерпретации хранить в утверждаемой клинической политике;
- положительный ответ на пункт о самоповреждении обрабатывать отдельно от общей суммы.

Не создавать медицинский диагноз на основании результата.

Если опросник не завершён, сохранять статус `in_progress`, но не формировать итоговый клинический результат.

Результаты сохранять с версией опросника, временем, этапом беременности и связанным контекстом.

# 10. Wellbeing Monitor и Screening Scheduler

Реализовать мониторинг самочувствия по трём независимым источникам:

1. Самооценки женщины.
2. Стандартизированные психологические шкалы.
3. Жалобы и сообщения о состоянии из чата.

Не создавать общий недоказанный `mental_health_score`.

## 10.1. Check-in

Предусмотреть простой опрос:

```text
Какое у вас сегодня настроение? 0–10
Насколько сильно вы сегодня тревожитесь? 0–10
Как вы оцениваете качество сна? 0–10, необязательно
```

Частота предложения — ориентировочно один раз в семь дней.

Пользователь вправе проходить check-in самостоятельно чаще.

Данные сохранять отдельными временными точками.

## 10.2. Повторные психологические опросники

Реализовать конфигурируемую логику:

- при подключении пользователя — предложить первичную оценку;
- позднее во время беременности — предложить повторную;
- после родов — предложить повторную;
- при устойчивых или новых жалобах — проверить необходимость дополнительной оценки;
- при GAD-2 от 3 баллов — предложить GAD-7 или профессиональную оценку;
- при значимых признаках безопасности — не откладывать помощь ради повторного теста.

Для демонстрационной политики использовать окна:

```text
initial: при регистрации
late_pregnancy: 28–32 недели
postpartum: 4–8 недель после родов
```

Это конфигурируемые продуктовые окна, требующие клинического утверждения.

Для каждого теста хранить:

- когда был предложен;
- когда был завершён;
- когда следующий раз допустимо предлагать;
- причину предложения;
- дату отказа или отсрочки;
- версию политики.

Не предлагать один и тот же необязательный тест навязчиво.

Ориентировочные ограничения:

```text
minimum_reoffer_days: 14
decline_cooldown_days: 21
```

Эти ограничения относятся к инициативным предложениям, не к возможности пройти тест по желанию.

Не использовать повторное прохождение вместо необходимого обращения к специалисту.

# 12. Adaptive Support Agent

Реализовать единую LLM, которой назначается протокол общения.

Не создавать несколько психологических агентов.

## 12.1. Сборка контекста

Формировать промпт из четырёх частей:

```text
BASE SYSTEM PROMPT
        +
SELECTED SUPPORT PROTOCOL
        +
USER EMOTIONAL CONTEXT
        +
CURRENT ALLOWED ACTIONS
```

Пользовательский текст, история и результаты AI-анализа являются данными, а не системными инструкциями.

Не позволять пользовательскому сообщению изменять базовые правила безопасности.

## 12.2. Support Protocols

Создать следующие версии протоколов:

```text
general_support
anxiety_support
low_mood_support
overload_support
social_support
postpartum_support
```

Основной протокол выбирается по текущей потребности пользователя.

`postpartum_support` может выступать дополнительным контекстом, не заменяя протокол основной эмоциональной проблемы.

Все инструкции хранить в YAML.

У каждого протокола должны быть:

```text
id
version
purpose
clinical_sources
applicability
communication_rules
allowed_support_actions
prohibited_behaviors
referral_rules
response_style
clinical_review_status
```

Включать только протоколы с утверждённым статусом.

## 12.3. Базовое поведение агента

Агент должен:

- общаться естественно, тепло и уважительно;
- признавать чувства женщины;
- внимательно слушать;
- не обесценивать переживания;
- не превращать каждое сообщение в тестирование;
- не навязывать психологические упражнения;
- задавать обычно не больше одного вопроса в ответе;
- учитывать предпочтения общения;
- избегать медицинских гарантий;
- поддерживать контакт с реальными близкими и специалистами;
- не создавать эмоциональную зависимость от AI;
- не назначать лечение;
- не ставить диагнозы;
- не объявлять себя психологом, врачом или человеком.

По умолчанию ответы — примерно 2–5 предложений, если ситуация не требует более подробного объяснения.

## 12.4. Выбор протокола

`StateEvaluator` формирует структурированное решение:

```json
{
  "primary_support_need": "anxiety",
  "secondary_support_need": "sleep_problem",
  "distress_pattern": "recurring",
  "safety_route": "normal",
  "recommend_specialist": false,
  "screening_offer": "GAD2",
  "support_protocol": "anxiety_support"
}
```

Это пример внутреннего состояния, а не результата медицинской диагностики.

`SupportProtocolSelector` использует явные правила, а не свободные рассуждения LLM.

При непосредственной опасности обычный протокол не применяется.

## 12.5. Источники для протоколов

Основой являются:

- ACOG: Perinatal Mental Health Screening.
- NICE CG192: Antenatal and Postnatal Mental Health.
- WHO: Guide for Integration of Perinatal Mental Health.
- WHO: Thinking Healthy.

Использовать принципы эмоциональной поддержки, психообразования, снижения напряжения и укрепления социальной поддержки.

Не переносить в чат-бот полноценные лечебные методики, которые должны проводиться подготовленными специалистами.

Не копировать защищённые тексты клинических материалов в коммерческий продукт без проверки прав использования.

# 13. Safety Guard

Реализовать независимый входной и выходной контроль.

## 13.1. Маршруты

```text
normal
recommend_professional
urgent
```

`normal` — обычная эмоциональная поддержка.

`recommend_professional` — поддержка с рекомендацией обратиться к квалифицированному специалисту.

`urgent` — заранее утверждённый сценарий для возможной непосредственной опасности.

## 13.2. На входе

Проверять возможные сигналы:

- самоповреждение и суицидальные высказывания;
- опасность причинения вреда ребёнку;
- выраженная дезориентация или возможные психотические симптомы;
- серьёзные акушерские тревожные симптомы;
- другие признаки непосредственной опасности.

Учитывать отрицания, цитаты, навязчивые нежелательные мысли и реальное намерение. Не приравнивать их автоматически.

При неопределённости использовать консервативную маршрутизацию, но не сообщать пользователю несуществующий диагноз.

## 13.3. На выходе

Jev проверяет ответ LLM на:

```text
unsupported_medical_claim
false_reassurance
unsafe_treatment_advice
missed_referral
missed_urgent_escalation
emotional_dependency_encouragement
```

Дополнительно использовать обычные программные правила.

Никакой AI Judge не считается единственным достаточным средством обеспечения безопасности.

## 13.4. Сбои

Если классификатор недоступен или результат нельзя надёжно интерпретировать:

- не считать сообщение автоматически безопасным;
- не создавать клинические выводы;
- применять консервативный шаблон или ограниченный безопасный режим;
- сохранить событие сбоя;
- не отправлять рискованные инициативные сообщения.

При недоступности LLM использовать утверждённый шаблон технического ответа.

Не отправлять сообщение пользователю до прохождения обязательных проверок.

## 13.5. Экстренные ситуации

Не обещать, что за чатом следит живой врач.

Не заявлять, что система автоматически вызовет помощь.

Показывать понятные способы получения срочной помощи с учётом страны пользователя, если страна известна и информация проверена.

При критической ситуации немедленно предоставлять безопасную реакцию в рамках текущего взаимодействия, а не запускать обычное тестирование.

# 14. Proactive Messaging Engine — самостоятельные сообщения ядра

**Это обязательный компонент MVP.**

Ядро должно иметь возможность первым отправлять сообщение в существующий чат женщины, без её нового входящего сообщения.

Инициативная коммуникация допускается только после явного согласия пользователя.

Не использовать её для искусственного увеличения вовлечённости или формирования эмоциональной зависимости.

## 14.1. Типы инициативных сообщений

Реализовать:

### `weekly_checkin`

Периодический вопрос о самочувствии.

Пример:

«Привет! Как ты себя чувствуешь в последние дни? Если хочется, можем немного поговорить».

### `questionnaire_due`

Пришло время предложить повторный опросник.

Пример:

«Если тебе удобно, можно снова пройти короткий опрос о самочувствии. Он поможет сравнить твои ответы с предыдущими. Это необязательно».

### `agreed_followup`

Женщина согласилась, чтобы система позже спросила о состоянии.

Пример:

«Ты рассказывала, что последние дни были непростыми. Как ты сегодня себя чувствуешь?»

Не упоминать конкретную чувствительную жалобу, если это неуместно или женщина запретила такие напоминания.

## 14.2. Стандартная политика частоты

Использовать конфигурацию:

```yaml
proactive:
  enabled_by_default: false

  allowed_start: "10:00"
  allowed_end: "19:00"

  quiet_start: "20:00"
  quiet_end: "09:00"

  weekly_checkin_days: 7

  minimum_gap_between_messages_hours: 72

  maximum_messages_7_days: 2
  maximum_messages_30_days: 5

  suppress_if_user_active_within_hours: 24

  unanswered_limit: 2
  unanswered_pause_days: 30

  allow_questionnaire_reminders: true
  allow_agreed_followups: true
  allow_reengagement_messages: false

  default_delivery_channel: "in_app"
  allow_sensitive_push_text: false
```

Это конфигурация поведения приложения, а не медицинский стандарт.

Пользователь должен иметь возможность полностью отключить инициативные сообщения.

## 14.3. Приоритеты отправки

При одновременном наличии нескольких оснований выбирать максимум одно сообщение.

Приоритет:

1. Согласованное пользователем последующее уточнение.
2. Предложение планового опросника.
3. Еженедельный check-in.

Если отправлено предложение опросника, обычный check-in за тот же период можно пропустить.

Не отправлять два сообщения подряд из-за двух одновременно наступивших событий.

Не отправлять инициативное сообщение, если в чате уже есть непрочитанное инициативное сообщение от ядра.

После двух инициативных сообщений без ответа поставить коммуникацию на паузу на 30 дней.

Если пользователь возобновил общение, пауза может быть снята в пределах его настроек согласия.

## 14.4. Дополнительные условия безопасности

Запретить инициативные сообщения:

- если пользователь не дал согласие;
- если коммуникация отключена;
- во время тихих часов;
- при недоступном или некорректном локальном времени;
- после удаления или деактивации профиля;
- при неопределённом состоянии доставки;
- если ранее уже отправлено сообщение с тем же `deduplication_key`;
- если недавно был зафиксирован экстренный сценарий и нет отдельно утверждённого плана последующего контакта.

Обычный worker **не должен пытаться вести активное кризисное наблюдение**.

Нельзя использовать отсутствие ответа как показатель клинического ухудшения.

## 14.5. Генерация инициативного текста

Для MVP использовать проверенные шаблоны как основной способ генерации.

Допускается необязательная адаптация формулировки через LLM, но она должна проходить обычную проверку безопасности.

Не создавать чрезмерно эмоциональные сообщения вроде:

- «Я скучала по тебе».
- «Почему ты давно не пишешь?»
- «Я беспокоюсь, что ты меня забыла».
- «Ты нужна мне».

Инициативное сообщение должно быть коротким, спокойным и не требовать обязательного ответа.

## 14.6. Фоновый планировщик

Создать процесс:

```text
python -m emo_core.workers.proactive_worker
```

Планировщик каждые пять минут:

1. Получает наступившие события из PostgreSQL.
2. Выбирает задания с блокировкой строк.
3. Повторно проверяет согласие пользователя.
4. Проверяет локальное время.
5. Проверяет ограничения частоты.
6. Проверяет активность и непрочитанные сообщения.
7. Проверяет допустимость конкретного сценария.
8. Формирует сообщение из разрешённого шаблона.
9. Сохраняет сообщение от `assistant` с `origin=proactive`.
10. Помечает задание выполненным.
11. Передаёт событие клиентскому приложению или в систему уведомлений.

Использовать транзакции PostgreSQL и `FOR UPDATE SKIP LOCKED` либо эквивалентный надёжный механизм.

Несколько экземпляров worker не должны отправлять одно событие дважды.

Запись сообщения и отметка о выполнении задания должны быть согласованы транзакционно.

При ошибке push-доставки уже записанное сообщение не должно создаваться повторно.

## 14.7. Доставка сообщений

В первую очередь реализовать **in-app chat delivery**.

Проактивное сообщение сохраняется как обычное сообщение ассистента и появляется в истории чата.

Фронтенд получает его через:

- запрос истории сообщений;
- и, при необходимости, SSE или WebSocket в будущей версии.

Push-уведомления реализовать через абстракцию `NotificationProvider`, но не делать интеграцию с конкретным мобильным провайдером обязательной для MVP.

Текст push-уведомления по умолчанию:

«У вас новое сообщение в приложении».

Не указывать на заблокированном экране сведения о тревоге, депрессии, результатах тестов или жалобах.

# 15. Memory Manager

Хранить три слоя памяти.

## 15.1. Краткосрочная

Последние сообщения текущего разговора.

## 15.2. Долгосрочная

Краткое резюме:

- важные переживания;
- повторяющиеся темы;
- предпочтения общения;
- важные события;
- упомянутые источники поддержки;
- действия, которые, со слов женщины, помогали.

## 15.3. Структурированная

Отдельные записи:

- жалобы;
- оценки;
- тесты;
- события;
- динамика.

Обновлять резюме примерно после 10–15 новых сообщений или значимого изменения контекста.

Не смешивать подтверждённые факты с модельными предположениями.

Все предположения должны иметь источник и время.

При длительном отсутствии новых данных не считать старые симптомы актуальными без уточнения.

Предусмотреть возможность пользователя просмотреть, исправить или удалить сохранённую персональную информацию в рамках политики хранения.

# 19. Тестирование

Реализовать unit- и integration-тесты.

Обязательные сценарии:

### Общение

- Сообщение обрабатывается и сохраняется.
- Последующая реплика использует предыдущий контекст.
- Новая беседа того же пользователя получает долговременную память.
- Изменение основного LLM-провайдера не ломает бизнес-логику.
- Недоступность LLM корректно обрабатывается.

### Жалобы

- Повторная жалоба обновляет существующую карточку.
- Одно сообщение может относиться к нескольким категориям.
- Отрицание симптома не создаёт подтверждённую жалобу.
- Чужая цитата не считается самоотчётом.
- Отсутствие новых сообщений не означает исчезновение жалобы.

### Опросники

- Баллы рассчитываются точно.
- Реверсивные пункты EPDS учитываются правильно.
- Сохраняются все прохождения.
- Незавершённый тест не попадает в расчёт динамики.
- Положительный ответ на пункт безопасности обрабатывается независимо от общей суммы.
- Повторный тест не предлагается слишком часто.
- GAD-2 от 3 баллов приводит к корректному предложению следующего шага.

### Протоколы поддержки

- Тревожная тема выбирает соответствующий протокол.
- Сниженное настроение не интерпретируется как установленная депрессия.
- Послеродовой контекст учитывается.
- Приоритет безопасности выше выбранного протокола.
- LLM не получает полномочия самостоятельно назначать лечение.

### Инициативные сообщения

- Без согласия ничего не отправляется.
- Сообщения отправляются в разрешённое время.
- Тихие часы работают.
- Ограничения частоты соблюдаются.
- Два проигнорированных сообщения приводят к паузе.
- Недавняя активность подавляет ненужное сообщение.
- Повторный запуск worker не создаёт дубликатов.
- Два конкурентных worker не выполняют одно задание дважды.
- Время корректно обрабатывается при смене часового пояса и переходе летнего времени.
- Проактивное сообщение появляется в истории как `assistant/proactive`.
- Экстренный сценарий не запускает обычные инициативные уведомления.

### Безопасность

- Опасный сигнал обрабатывается до обычной генерации.
- Небезопасный ответ LLM блокируется.
- При ошибке Jev не возникает фиктивного заключения.
- Медицинские заверения не проходят проверку.
- Пользовательский текст не может подменить системный промпт.
- Чувствительные данные не записываются в обычные логи.

### Многопользовательская работа

- Пользователь A не получает сообщения пользователя B.
- Пользователь A не видит тесты пользователя B.
- Пользователь A не может изменить настройки пользователя B.
- Параллельные запросы разных пользователей корректно обрабатываются.
- Удаление данных одного пользователя не затрагивает других.

Для безопасности дополнительно сформировать набор русскоязычных тестовых диалогов, который впоследствии можно передать клиническому эксперту для разметки и проверки.

# 20. Защита персональных данных

Система работает с чувствительными сведениями о психическом и физическом самочувствии.

Реализовать:

- проверку авторизации на всех endpoints;
- изоляцию пользователей;
- минимизацию отправляемых внешним AI данных;
- защищённое хранение конфигурационных секретов;
- отсутствие медицинских данных в обычных application logs;
- управляемое хранение и удаление;
- версионирование правил безопасности;
- возможность отключить внешнюю AI-обработку, если она не разрешена;
- отсутствие чувствительной информации в push-уведомлениях.

При передаче текста Jev и LLM должна быть возможность настроить разрешённого провайдера и регион обработки.

Не утверждать, что использование внешнего AI автоматически соответствует требованиям законодательства.

Юридическое согласование обработки данных и клиническое утверждение правил остаются обязательными условиями реального публичного запуска.

# 22. Критерии готовности

Задача считается завершённой, когда:

1. Проект запускается одной командой `docker compose up --build`.
2. Миграции автоматически или документированно применяются.
3. Доступна документация FastAPI.
4. Работает многопользовательский чат.
5. Пользовательская память сохраняется между сессиями.
6. Jev интегрирован и возвращает структурированные результаты при наличии API-ключа.
7. Жалобы накапливаются без дублирования карточек.
8. Работают доступные и корректно сконфигурированные опросники.
9. Повторные прохождения сохраняются.
10. Доступна динамика шкал и самочувствия.
11. LLM получает назначенный протокол поддержки.
12. Safety Guard блокирует опасные ответы.
13. Ядро самостоятельно отправляет сообщения в чат по заданным условиям.
14. Проактивные сообщения не дублируются при конкурентной работе.
15. Пользователь может отключить инициативную коммуникацию.
16. Данные разных пользователей полностью изолированы.
17. Автоматические тесты выполняются успешно.
18. В README описаны установка, запуск, API, настройки и ограничения.
19. Неактивированные клинические материалы и отсутствующие юридические разрешения явно перечислены, а не скрыты.
20. Нет фиктивных заглушек, выдаваемых за рабочие медицинские функции.

# 23. Итоговые инструкции разработчику

Главные приоритеты:

**Первый — простота архитектуры.** Не усложняй систему без технической необходимости.

**Второй — полнота реализации.** Каждый предусмотренный модуль должен иметь работающие функции и тесты.

**Третий — строгая персональная изоляция.** Система многопользовательская с первого дня.

**Четвёртый — качественная эмоциональная поддержка.** Естественный разговор важнее попыток автоматически оценить каждую эмоцию.

**Пятый — безопасность.** Клиническая маршрутизация, медицинские ограничения и критические события не должны зависеть только от свободной генерации LLM.

**Шестой — контролируемая инициативность.** Ядро действительно может писать первым, но только с согласия, в уместное время и с ограниченной частотой.

**Седьмой — модульность AI.** Основную LLM, Jev и механизм уведомлений можно заменить без переписывания бизнес-логики.

Не завершай работу на уровне архитектуры или отдельных примеров. Создай реальный проект, проверь его запуск и исправь ошибки.

В конце предоставь краткий отчёт: какие компоненты реализованы, какие тесты запущены и прошли, как стартовать систему, какие внешние ключи нужны и что именно требует клинического или юридического утверждения перед реальной эксплуатацией.
