# Конфигурация

Команды и пути приведены относительно корня самостоятельного проекта `emo_core/`. Настройки читает `emo_core/core/config.py`: переменные процесса имеют приоритет над `.env`. `get_settings()` кэширует результат в процессе. Compose получает `.env` через `env_file`; шаблон для новой установки — [.env.example](../.env.example).

## Подготовка файла

```bash
poetry run emo-config init-env
poetry run emo-config check-config
```

`init-env` создаёт файл при отсутствии, заполняет недостающие локальные секреты и выставляет `0600`. Существующие значения не заменяет. Если `DATABASE_URL` уже содержит пароль, использует его при заполнении `POSTGRES_PASSWORD`. Ключи внешних моделей и согласие на их использование задаёт оператор.

Пароли со спецсимволами в `.env` заключайте в одинарные кавычки. В `DATABASE_URL` пароль должен быть URL-encoded. Не помещайте ключ в URL провайдера: адреса с логином, паролем, query или fragment запрещены.

`.env`, его варианты, `examples/client.env` и `.venv` исключены из Git. `.env` также исключён из Docker build context. Для примера клиента используйте [examples/client.env.example](../examples/client.env.example): пользовательский JWT в `EMO_API_TOKEN` отличается от серверных ключей моделей.

## Сервер, БД и авторизация

В таблицах указаны значения по умолчанию класса `Settings`. Шаблон `.env.example` намеренно включает development/mock и демо-авторизацию; после `init-env` используются его значения.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `APP_ENV` | `development` | `development`, `test` или `production` |
| `LOG_LEVEL` | `INFO` | Уровень application logs |
| `EMO_HTTP_PORT` | `8086` в Compose | Публикуемый HTTP-порт; не поле `Settings` |
| `DATABASE_URL` | `postgresql+asyncpg://localhost/emo` | DSN приложения и миграций; для Compose хост `db` |
| `POSTGRES_USER`, `POSTGRES_DB` | `emo`, `emo` в Compose | Начальная учётная запись и БД контейнера |
| `POSTGRES_PASSWORD` | — | Пароль начальной учётной записи Compose |
| `DB_POOL_SIZE`, `DB_MAX_OVERFLOW` | `10`, `20` | Постоянные и дополнительные соединения каждого процесса; не лимит генераций AI |
| `JWT_ISSUER`, `JWT_AUDIENCE` | `https://identity.example.invalid/`, `emo-core` | Ожидаемые `iss` и `aud` основного JWT |
| `JWT_JWKS_URL` | пусто | URL публичных RSA-ключей; в production обязателен HTTPS |
| `DEMO_AUTH_ENABLED` | `false` | Выпуск и приём HS256 для двух демо-профилей |
| `DEMO_JWT_SECRET` | пусто | Ключ подписи демо и консоли, минимум 32 символа при их использовании |
| `APP_LOGIN`, `APP_PASSWORD` | пусто | Вход в консоль; задаются вместе, пароль от 12 символов |
| `CONSOLE_SESSION_HOURS` | `8` | Срок сессии консоли, 1–72 часа |
| `API_KEY_TTL_DAYS` | `30` | Срок демо-токена с `purpose=api`, 1–365 дней |
| `ADMIN_API_TOKEN` | пусто | Отдельный секрет заголовка `X-Admin-Token`, минимум 32 символа |
| `MODEL_SECRETS_KEY` | пусто | Fernet-ключ для ключей моделей, введённых через API реестра |
| `MODEL_CREDENTIALS` | `{}` | JSON-словарь дополнительных именованных ключей |

Изменение `POSTGRES_PASSWORD` в файле не меняет пароль существующего volume. Ротация требует смены пароля в самой БД и согласованного обновления DSN. Потеря `MODEL_SECRETS_KEY` делает сохранённые шифротексты нечитаемыми: ключи профилей потребуется ввести заново либо заменить env-ссылками.

## AI и приватность

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `AI_MODE` | `disabled` | `mock`, `live`, `disabled`; выбранный в БД режим имеет приоритет |
| `EXTERNAL_AI_ALLOWED` | `false` | Разрешение оператора на внешнюю обработку |
| `AI_PROCESSING_REGION` | пусто | Согласованный оператором регион обработки, обязателен для live |
| `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY` | пусто | OpenAI-совместимый endpoint, точный ID и ключ генератора |
| `LLM_TIMEOUT_SECONDS` | `30` | Тайм-аут обращения к генератору |
| `LLM_EXTRA_BODY` | `{}` | JSON с дополнительными полями запроса провайдера |
| `LLM_MAX_OUTPUT_TOKENS` | `600` | Максимум токенов ответа, 64–8000 |
| `TYPESAFE_BASE_URL` | `https://api.typesafe.ai` | Endpoint TypeSafe |
| `TYPESAFE_API_KEY` | пусто | Ключ Jev |
| `JEV_MODEL` | `jev-1.14.0` | Закреплённая версия; `jev-latest` запрещена |
| `JEV_TIMEOUT_SECONDS` | `15` | Тайм-аут Jev |
| `JEV_MAX_RETRIES` | `1` | Число повторов SDK, 0–3 |
| `JEV_THRESHOLD` | `0.7` | Основной порог входных маркеров |
| `JEV_REVIEW_THRESHOLD` | `0.35` | Порог дополнительного внимания; меньше основного |
| `JEV_SENSITIVE_REVIEW_THRESHOLD` | `0.12` | Пониженный порог чувствительных входных маркеров |
| `JEV_OUTPUT_THRESHOLD` | `0.5` | Отдельный порог блокировки готового ответа |
| `ALLOWED_LLM_HOSTS` | пусто | Разрешённые HTTPS-хосты LLM через запятую |
| `ALLOWED_JEV_HOSTS` | `api.typesafe.ai` | Разрешённые HTTPS-хосты Jev через запятую |
| `CONTEXT_WINDOW_TOKENS` | `256000` | Окно запроса к LLM, 8192–4000000 |
| `CONTEXT_SAFETY_MARGIN_TOKENS` | `16000` | Резерв внутри окна; дополнительно вычитается максимум ответа |
| `ANONYMIZE_OUTBOUND` | `user` | `user` — личный выбор с включением по умолчанию; `always`/`never` — решение оператора |

Для live нужны оба ключа, ID LLM, разрешение оператора, регион и разрешённые HTTPS-адреса. Дополнительно каждый профиль должен передать `external_ai_consent=true` через `PATCH /settings`. Без согласия его текст моделям не отправляется.

`LLM_EXTRA_BODY` зависит от контракта провайдера. Значение из текущего шаблона в комментарии приведено как пример, а не как универсальный параметр. Поля накладываются поверх стандартного запроса адаптера, поэтому `model`, `messages`, `temperature` и `max_tokens` в этом словаре переопределят одноимённые параметры. Используйте его для дополнительных опций провайдера.

## Общие модели

Реестр хранится в PostgreSQL: профили `llm`/`jev`, выбранные роли, режим и журнал ревизий. Доступ администратора проверяется через `X-Admin-Token` либо JWT сессии консоли в том же заголовке. Пользовательский JWT подходит для чтения `/models`, но не для `/admin/*`.

Для ключа из окружения используйте `credential_ref: "llm_default"` или `"jev_default"`. Дополнительные ссылки задаются так:

```dotenv
MODEL_CREDENTIALS='{"backup_llm":"<ключ-провайдера>","second_jev":"<ключ-провайдера>"}'
```

Значения остаются на сервере; API возвращает только имена ссылок и признак заполнения. Альтернатива — поле `api_key` при создании/правке профиля: backend шифрует его через `MODEL_SECRETS_KEY`. Сам ключ и шифротекст в ответах отсутствуют.

Пример создания профиля: `POST /api/v1/emo/admin/models` с административной авторизацией.

```json
{
  "kind": "llm",
  "name": "Основной генератор",
  "model": "<точный-id-модели>",
  "base_url": "https://<разрешённый-хост>/v1",
  "timeout_seconds": 30,
  "credential_ref": "llm_default"
}
```

`GET /admin/models` возвращает профили и текущую `runtime.revision`. После создания/правки перечитайте её. Для выбора отправьте `PATCH /admin/model-runtime`:

```json
{
  "expected_revision": 3,
  "ai_mode": "live",
  "llm_profile_id": "<UUID-профиля-llm>",
  "jev_profile_id": "<UUID-профиля-jev>"
}
```

Число `3` — пример; используйте прочитанную ревизию. При конфликте вернётся 409. Пропущенное поле оставляет выбор, `null` у `llm_profile_id`/`jev_profile_id` возвращает роль к `.env`. Режим меняется отдельно и не сбрасывается этим `null`.

`PATCH /admin/models/{id}` изменяет профиль. Пропущенный ключ сохраняется; передать `null` нельзя. Профиль создаётся без платной проверки ключа и без автоматической загрузки каталога провайдера. Ошибку реального обращения покажет отчёт обработки.

Профили и режим из БД имеют приоритет над соответствующими параметрами `.env`. Если ключи живут только в БД, исходный `AI_MODE` в файле оставьте `disabled` (в development допустим mock), а live включите через реестр после создания обеих ролей. Иначе стартовая проверка live потребует ключи из окружения ещё до обращения к БД.

Смена реестра действует на следующие сообщения всех пользователей. Уже принятый запрос использует согласованный снимок; исторические отчёты сохраняют модели своей реплики. Изменения отражаются в `GET /admin/model-events` без секретов.

## Worker, хранение и политики

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PROACTIVE_WORKER_ENABLED` | `true` | Запуск цикла worker; не заменяет личное согласие |
| `PROACTIVE_POLL_SECONDS` | `300` | Интервал цикла, положительное число секунд |
| `RETENTION_DAYS` | `365` | Возраст данных для явного запуска `emo-config prune` |
| `POLICY_DIR` | пусто | Внешний каталог YAML-политик; пусто — встроенные политики |

При внешнем `POLICY_DIR` каталог должен быть доступен процессам API и worker. В Compose его нужно включить в образ либо подключить отдельным volume.

## Применение изменений

Правки `.env` требуют перезапуска локальных процессов или пересоздания контейнеров:

```bash
docker compose up -d --force-recreate api worker migrate
```

Правки профилей через API действуют без перезапуска. Изменение YAML при работе из образа требует его пересборки. Для production обязательны PostgreSQL/asyncpg, RS256/JWKS и документированное одобрение safety policy; mock и демо-авторизация запрещены. Клинические статусы описаны в [ARCHITECTURE.md](ARCHITECTURE.md#материалы-и-границы-готовности).

## Отбор сообщений перед JEV

`JEV_GATE_ENABLED=true` включает предварительный Noul для потенциально нейтральных сообщений. `JEV_GATE_SKIP_THRESHOLD=0.05` (допустимо 0–0,1) — верхняя оценка для пропуска полного анализа. Явные темы и неоднозначные короткие продолжения сразу направляются на полный анализ; ошибка отбора также не разрешает пропуск. Это инженерный порог, требующий проверки на размеченных данных. `false` отключает отбор.
