## Файлы и процессы

| Путь / служба | Назначение |
|---|---|
| `/opt/emo-core/source` | Git checkout, ветка `master` |
| `/opt/emo-core/source/emo_core` | Рабочая папка самостоятельного приложения |
| `/opt/emo-core/source/emo_core/.env` | Реальная серверная конфигурация |
| `/opt/emo-core/ops` | Зафиксированные настройки развёртывания и скрипты обслуживания |
| `/opt/emo-core/backups` | Локальные дампы PostgreSQL |
| `emo-core.service` | Запуск Compose после Docker и сети |
| `nginx.service` | HTTPS на 443 и перенаправление HTTP на HTTPS |
| `snap.certbot.renew.timer` | Автоматическое продление сертификатов современным Certbot |
| `emo-core-backup.timer` | Ежедневный дамп БД |

Образ `emo-core:server` собран на сервере из исходного Dockerfile: Python 3.12 и Poetry 2.1.3. API, worker и миграции используют один образ. У API/worker настроены перезапуск, ограничения памяти и размера Docker-логов. PostgreSQL хранит данные в отдельном volume Compose.

API опубликован только на `127.0.0.1:8086`; PostgreSQL не публикует порт хоста. Nginx передаёт запросы и адрес клиента в API. Доверие forwarded-заголовкам рассчитано на эту схему с закрытым прямым доступом к backend; не меняйте привязку API на публичную без пересмотра настройки.

Состояние `active (exited)` у `emo-core.service` нормально: это oneshot-служба, запускающая контейнеры в фоне. Сами API и БД имеют healthcheck; worker работает отдельным процессом. Миграции должны завершиться с кодом 0.

Исходники серверных настроек сохранены локально в [deployment/server](../deployment/server). На сервер они установлены отдельно от Git checkout: обновление кода приложения не затирает действующую конфигурацию.

## Проверка состояния

На сервере:

```bash
systemctl status emo-core --no-pager
cd /opt/emo-core/source/emo_core
docker compose -f docker-compose.yml -f /opt/emo-core/ops/compose.server.yml ps -a
curl --fail --silent https://81.31.245.115/health
docker compose -f docker-compose.yml -f /opt/emo-core/ops/compose.server.yml logs --tail=50 api worker
```

Не выводите `docker compose config` или полный `docker inspect` в общедоступные отчёты: они могут раскрыть окружение. Для проверки синтаксиса используйте `config --quiet`.

## Обновление приложения

```bash
/opt/emo-core/ops/update.sh
```

Скрипт сначала сохраняет текущую БД, затем выполняет `git pull --ff-only origin master`, собирает образ и ждёт готовности контейнеров. При ошибке Git или сборки останавливается. `.env` остаётся игнорируемым локальным файлом. Обновление миграций выполняет сервис `migrate`.

Скрипт обновляет код приложения. Изменения `ops` устанавливаются отдельно после проверки: локальные образцы находятся в `deployment/server/`. Не удаляйте volume для обычного обновления.

После изменения `.env`:

```bash
systemctl restart emo-core
```

Это применяет настройки Compose и перезапускает сервисы. Смена `POSTGRES_PASSWORD` в файле не меняет пароль существующей БД; порядок ротации описан в [CONFIGURATION.md](CONFIGURATION.md).

## HTTPS

Для самого IP выпущен доверенный сертификат Let's Encrypt с профилем `shortlived`. Получение сначала проверено на staging, затем выдан рабочий сертификат. Механизм описан в [инструкции Let's Encrypt для IP-сертификатов](https://letsencrypt.org/2026/03/11/shorter-certs-certbot.html).

Файлы сертификата находятся в `/etc/letsencrypt/live/emo-core-ip/`. HTTP-путь `/.well-known/acme-challenge/` обслуживается из `/var/www/emo-acme`; остальной HTTP перенаправляется на HTTPS. Deploy-hook `/opt/emo-core/ops/renew-deploy-hook.sh` проверяет конфигурацию и перезагружает Nginx после продления.

Автоматическое продление выполняет Certbot 5.9.0 из Snap. Дублирующий timer старого Certbot 2.9 отключён. Проверка без замены рабочего сертификата:

```bash
snap run certbot renew --cert-name emo-core-ip --dry-run --run-deploy-hooks --non-interactive --no-random-sleep-on-renew
```

Флаг отключения случайной задержки нужен только для ручной проверки. В обычном таймере задержка остаётся стандартной. Для проверки срока сертификата:

```bash
openssl x509 -in /etc/letsencrypt/live/emo-core-ip/fullchain.pem -noout -dates
systemctl list-timers snap.certbot.renew.timer --no-pager
```

## Резервные копии

`emo-core-backup.timer` запускается ежедневно после 03:15 МСК со случайной задержкой до 10 минут. Скрипт делает `pg_dump --format=custom`, сначала пишет временный файл, затем переименовывает его в `.dump`. Каталог и файлы закрыты от других пользователей, файлы имеют права `0600`. Хранятся собственные дампы за последние семь суток; живые записи приложения эта очистка не удаляет.

Ручной запуск:

```bash
systemctl start emo-core-backup.service
systemctl status emo-core-backup.service --no-pager
ls -lh /opt/emo-core/backups
```

Восстановление проверено через `pg_restore --exit-on-error` в отдельную временную БД: восстановлены все 18 таблиц. Рабочая база при проверке не изменялась. Для проверки нового дампа также используйте отдельную БД; подмена рабочей требует отдельной процедуры обслуживания.

Эти копии находятся на том же сервере и не защищают от потери всего диска. Внешнее хранилище резервных копий не подключалось.
