# FemFedora

Исследовательское рабочее пространство Pregnancy State Platform: клинические правила, подготовка данных, эксперименты и ML-модели для поддержки ведения беременности.

Система предназначена для исследовательского прототипирования и подготовки к клинической валидации. Она не заменяет решение врача и не должна использоваться для автоматического назначения или отмены лечения.

## Установка окружения

Требуются Python 3.11 и Poetry 2.x. Настройка в `poetry.toml` создаёт окружение в корневой папке `.venv`. Из корня проекта:

```bash
poetry config virtualenvs.in-project true --local
poetry env use python3.11
poetry lock
poetry install --all-groups
poetry run python --version
poetry run python -m unittest discover -s tests
poetry run jupyter lab
```

`pyproject.toml` содержит зависимости для подготовки данных, обучения, графиков, ноутбуков и создания DOCX. Группа `dev` добавляет `pytest`; `--all-groups` устанавливает её вместе с основными зависимостями. Для преобразования исходного UCI `.xls` при полной повторной подготовке данных отдельно нужен LibreOffice (`soffice`); это системное приложение, оно не устанавливается через Poetry.

На macOS для LightGBM установите системный OpenMP: `brew install libomp`. Затем проверьте `poetry run python -c "import catboost, lightgbm"`.

```text

├── data/                  # Датасеты по стадиям подготовки
```

Все правила структуры собраны в этом файле. Вложенные папки не содержат отдельных README.

## Документы — `docs/`

Здесь хранятся спецификации, внешние материалы и документы проекта. Текущая клинико-техническая спецификация находится в `docs/Pregnancy_State_Platform_Final_RU.pdf`. Статья `docs/PULSE framework.pdf` используется как архитектурная исследовательская референция для будущего продольного мультимодального слоя, но не как готовая клиническая модель.

## База знаний — `knowledge-base/`

Папку можно открыть в Obsidian как отдельный vault. Точка входа — `knowledge-base/Home.md`.

- `00-inbox/` — быстрые входящие заметки;
- `10-project/` — цели, границы, дорожная карта и состояние проекта;
- `20-domain/` — клинические понятия, термины и словарь данных;
- `30-decisions/` — журнал архитектурных, продуктовых и исследовательских решений;
- `40-meetings/` — заметки встреч и договорённости;
- `50-future-ideas/` — возможные направления развития и архитектурные гипотезы;
- `attachments/` — изображения и файлы, встроенные в заметки;
- `90-archive/` — неактуальные материалы, сохранённые для истории.

Эталон продукта и текущий ML-scope разведены: `knowledge-base/10-project/00-product-canon.md` описывает долгосрочный контракт, а `knowledge-base/10-project/01-current-ml-scope.md` — ближайший план разработки.

Перенос исходной спецификации v3.0 проверяется через `knowledge-base/10-project/06-source-traceability.md`; постраничный аудит хранится в `research/reports/pregnancy_platform_kb_audit.md`.

## Исследования — `research/`

- `literature/` — обзоры публикаций и заметки по источникам;
- `notebooks/` — Jupyter-ноутбуки для анализа и проверки гипотез;
- `experiments/` — результаты отдельных исследовательских запусков;
- `reports/` — промежуточные выводы и исследовательские отчёты.

Для каждого эксперимента необходимо фиксировать цель, версию данных, конфигурацию, метрики и вывод. Повторно используемая логика переносится из ноутбуков в `src/`.

## Данные — `data/`

- `raw/` — неизменяемые исходные данные;
- `external/` — данные из внешних открытых или лицензированных источников;
- `interim/` — промежуточные результаты очистки и преобразований;
- `processed/` — готовые к анализу и обучению наборы;
- `samples/` — небольшие обезличенные примеры для тестов и документации.

Правила работы с данными:

1. Файлы в `raw/` не редактируются вручную.
2. Для каждого набора фиксируются источник, дата получения, лицензия, схема и шаги подготовки.
3. Персональные и медицинские данные нельзя добавлять в Git.
4. Для больших наборов следует использовать отдельное хранилище, DVC или Git LFS.
5. Код и ноутбуки работают с путями относительно корня проекта.

Открытые наборы регистрируются в `data/registry/`: там хранятся версии, официальные URL, лицензии, контрольные суммы и результаты первичной проверки. Сами тяжёлые файлы исключены из обычного Git и восстанавливаются скриптом загрузки.

## Код — `src/`

- `clinical_rules/` — версионируемые клинические правила и калькуляторы;
- `data/` — загрузка, проверка и преобразование данных;
- `features/` — построение признаков;
- `models/` — Python-классы моделей и описания архитектур;
- `training/` — обучение, подбор параметров и сохранение чекпоинтов;
- `evaluation/` — метрики, калибровка и валидация;
- `inference/` — загрузка готовых моделей и получение прогнозов.

В `src/models/` хранится код классов моделей. Бинарные файлы обученных моделей туда не помещаются.

## Модели и конфигурации — `models/`

- `models/configs/architectures/` — конфигурации архитектур моделей;
- `models/configs/data/` — параметры выборок и подготовки данных для моделей;
- `models/configs/training/` — параметры обучения и воспроизводимости;
- `checkpoints/` — промежуточные состояния обучения;
- `exported/` — готовые к инференсу модели (`.onnx`, `.pt`, `.joblib` и другие);
- `registry/` — карточки версий моделей, метрики и статус проверки.

Все конфигурации моделей хранятся внутри `models/configs/`. Тяжёлые файлы из `models/checkpoints/` и `models/exported/` исключены из обычного Git; для них требуется объектное хранилище, DVC или Git LFS. Конфигурации и реестр моделей сохраняются в Git.

Для каждой версии модели в `models/registry/` создаётся Markdown- или YAML-карточка со следующими полями:

- уникальный идентификатор и дата;
- назначение и момент прогноза;
- версия кода и данных;
- путь к конфигурации;
- метрики и результаты валидации;
- известные ограничения;
- статус: эксперимент, теневой режим, проверена или архивирована;
- расположение бинарного артефакта.

## Тесты — `tests/`

- `unit/` — быстрые тесты функций, клинических правил и классов;
- `integration/` — полные сценарии подготовки данных, обучения, экспорта и инференса.

## Рабочий поток модели

```text
data/raw
  → data/interim
  → data/processed
  → research/notebooks
  → src/models + src/training
  → models/checkpoints
  → src/evaluation
  → models/exported + models/registry
```

Клиническое правило не заменяется моделью автоматически. ML-модель сначала оценивается как независимый сигнал, после чего проходит временную, внешнюю и проспективную проверку.

## Открытые данные для первого ML-этапа

В проекте зарегистрированы CDC/NCHS Natality 2023–2024, CTU-UHB CTG, UCI Cardiotocography и TPEHG. Тяжёлые архивы находятся локально в `data/external/` и не попадают в обычный Git. Их происхождение, лицензии и ограничения описаны в `data/registry/open_datasets.json` и в базе знаний.

Дополнительно локально загружены современный архив Collaborative Perinatal Project v3.3.1, авторский Multiomics Preeclampsia (Marić et al.) и полные public-use архивы NLSY79 и NLSY79 Child & Young Adult. Для DREAM/SDY2187 сохранён официальный манифест; сам пакет ImmPort требует авторизованной загрузки. Состояние, URL и версии новых источников — в `data/registry/longitudinal_datasets.json`. В каждом каталоге `data/external/<набор>/DATASET.md` описаны поля, зерно данных, цель исследования и применимость к проекту.

Воспроизводимый поток:

```bash
python -m src.data.download_open_datasets
python -m src.data.prepare_open_datasets
python -m src.data.profile_open_datasets
```

Результаты подготовки:

- `data/processed/cdc_natality/natality_ml_2023_2024.sqlite` — табличная база для лёгких PTB, GDM и HDP-proxy baseline;
- `data/processed/ctu_uhb_ctg/record_index.csv` — индекс КТГ-сигналов и метаданных;
- `data/processed/tpehg/record_index.csv` — индекс EHG-сигналов;
- `data/processed/uci_cardiotocography/ctg_features.csv` — очищенный учебный feature benchmark.

## CDC HDP-proxy: общие фолды и временная проверка

Исследование риска по анамнезу и данным до беременности находится в
[`research/notebooks/preeclampsia_cdc/`](research/notebooks/preeclampsia_cdc/):
`01_prepare_data.ipynb` создаёт общую одноплодную когорту 2023+2024 без зарегистрированной хронической АГ и пять
фолдов, `02_train_baselines.ipynb` обучает фиксированные baseline, выполняет вложенный подбор с прогрессбарами и затем обучает итоговые модели на всей когорте,
`03_evaluate_folds.ipynb` показывает распределение внешних метрик настроенной процедуры, фиксированные ориентиры и графики,
`04_feature_correlations.ipynb` исследует связи между признаками,
`05_feature_importance.ipynb` отдельно оценивает важность на отложенных фолдах,
`06_temporal_validation.ipynb` обучает на 2023, отдельно подбирает параметры только по 2023 и проверяет перенос на 2024 с
фиксированным порогом, двумя отдельно обученными моделями составных исходов,
аудитом ART/подгрупп, числами на 1000 записей и бутстрепом. Отдельный флаг импутации расы из исходных архивов проверяется в 03/06, но не подаётся в модели. Основные сравнения включают сплайн-логистику,
HistGradientBoosting, CatBoost и LightGBM; обоснование и ограничения выбора — в
[`MODEL_BENCHMARKS.md`](research/notebooks/preeclampsia_cdc/MODEL_BENCHMARKS.md).
Вложенная CV в 02 использует пять смешанных внешних фолдов и четыре
внутренних фолда для выбора параметров каждой модели и типа модели. 03 показывает
распределение внешних метрик; 06 — абляции по 2023 и исследовательский перенос.
02 отдельно выбирает конфигурации на всех фолдах 2023+2024 и обучает итоговые варианты на всей когорте. Схема и предел оценки — в
[`HYPERPARAMETER_SEARCH_PROTOCOL.md`](research/notebooks/preeclampsia_cdc/HYPERPARAMETER_SEARCH_PROTOCOL.md).
В этой рабочей папке когорта уже подготовлена: для основного прогона запускайте
`02` → `03`, для отдельной временной проверки — `06`. Ноутбук `01` запускайте
только при намеренной пересборке данных: повторная запись Parquet может изменить
контрольную сумму и сделать сохранённые результаты несовместимыми. Результаты 2024
уже просматривались в этой рабочей среде, поэтому новый прогон не будет
слепым тестом.
Обучение выполняется пользователем; полный общий Parquet уже подготовлен локально.
Критическая проверка исхода и узкий план обогащения — в
[`FEATURE_ENRICHMENT_AND_CLINICAL_AUDIT.md`](research/notebooks/preeclampsia_cdc/FEATURE_ENRICHMENT_AND_CLINICAL_AUDIT.md).
Точный состав входа, маски пропусков и маршрут ART — в
[`MODEL_INPUT_CONTRACT.md`](research/notebooks/preeclampsia_cdc/MODEL_INPUT_CONTRACT.md).
Решения по повторному экспертному разбору и план проверки составных исходов — в
[`EXPERT_REVIEW_DECISIONS.md`](research/notebooks/preeclampsia_cdc/EXPERT_REVIEW_DECISIONS.md).
Определение исхода, литература и ограничения — в
[`research/reports/preeclampsia_cdc_hdp_proxy.md`](research/reports/preeclampsia_cdc_hdp_proxy.md).

Для запуска CDC на уже подготовленной когорте:

```bash
poetry install --with dev
poetry run jupyter lab research/notebooks/preeclampsia_cdc
```

В начале 02 проверяются аудит когорты, версии библиотек, отпечатки существующих результатов, место на диске и объём ОЗУ. Выполняйте 02 сверху вниз; после прерывания снова запускайте его с начала — завершённые результаты проходят проверку и используются повторно. Полный подбор на CDC требует 440 внутренних оценок, 30 внешних прогнозов моделей и ещё 110 проверок для итогового выбора; он не запускается при создании ноутбуков. Все клинические ограничения остаются обязательными даже после технически успешного обучения.

## CDC PTB: модель прогноза для женщины

Шесть выполненных ноутбуков находятся в [`research/notebooks/preterm_cdc/`](research/notebooks/preterm_cdc/). Они готовят одноплодную когорту живорождений CDC, сравнивают мультиномиальную логистику, LightGBM и CatBoost, проводят подбор параметров, абляции и перестановочную важность. Шестой ноутбук строит прогноз для одной женщины на указанном сроке, проверяет входы и маски, отказывает при незаполненных или внеобластных признаках, измеряет точность на допустимой части 2024 года, сравнивает модель с простым правилом анамнеза и экспортирует модель. Фолдов нет: 2023 один раз разделён на обучение, валидацию и калибровку. Подробности — в [README набора](research/notebooks/preterm_cdc/README.md) и [контракте модели](research/notebooks/preterm_cdc/WOMAN_FORECAST_CONTRACT.md).
